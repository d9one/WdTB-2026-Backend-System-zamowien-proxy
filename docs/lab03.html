ZadanieA · Pytania kontrolne przy stanowisku

Reguły w GitHub Actions sprawdzają kod, ale nie sprawdzają, czy rozumiecie, co ten kod robi. Dlatego w trakcie pracy prowadzący podchodzi do stanowiska, a każda osoba z zespołu losuje jedno pytanie z poniższej listy i odpowiada na nie na własnym projekcie: w kodzie encji, w logu uruchomienia albo w konsoli H2. Odpowiedź trwa około minuty.

  1. W której tabeli powstała kolumna klucza obcego dla wybranej relacji i dlaczego właśnie po tej stronie, a nie po drugiej?
  2. Co się stanie, gdy w data.sql wiersz tabeli podrzędnej (np. rezerwacja) znajdzie się przed wierszem tabeli nadrzędnej (np. gościem)? Jaki komunikat pojawia się w logu?
  3. Co zmienia nullable = false w @JoinColumn? Pokażcie różnicę w poleceniu create table w logu.
  4. Po co w @OneToMany jest mappedBy i co Hibernate utworzyłby bez niego?
  5. Co oznacza fetch = FetchType.LAZY przy @ManyToOne? Kiedy Hibernate pobiera wiersz nadrzędny?
  6. Pokażcie w konsoli H2 zapytanie łączące dwie tabele (join), które odpowiada na jedno z pytań inwestora z Waszego pomysłu.
  7. Dlaczego relację wiele-do-wielu modelujemy encją łączącą z dwiema relacjami @ManyToOne, a nie adnotacją @ManyToMany?

Ocena zespołu wynika z przebiegu w GitHub Actions (część H). Osoba, która nie potrafi odpowiedzieć na wylosowane pytanie, otrzymuje ocenę o jeden stopień niższą od oceny zespołu.

Narzędzia AI

Z asystentów AI możecie korzystać. Pytania kontrolne sprawdzają zrozumienie, nie autorstwo każdej linii, dlatego najlepiej prosić asystenta o wyjaśnienie, a nie o gotowy kod. Przykład polecenia, które przygotowuje do pytań z listy:

TeoriaB · Wprowadzenie: klucz obcy, @ManyToOne, dane powiązane

Na zajęciach prowadzący omawia B1 i B3 (ok. 12 minut). B2 i B4 to ściąga: wracacie do nich w trakcie pracy.

B1. Klucz obcy to kolumna po stronie „wiele”

Na LAB 02 tabele były osobne: rezerwacja nie wiedziała, którego stolika dotyczy. W bazie relacyjnej takie powiązanie to klucz obcy: kolumna w jednej tabeli, która przechowuje id wiersza z drugiej tabeli. Kolumna zawsze leży po stronie „wiele”: wiele rezerwacji wskazuje na jeden stolik, więc kolumna table_id jest w tabeli reservation, a nie w cafe_table. Stolik nie ma kolumny „rezerwacje”, bo jedna kolumna nie pomieści wielu numerów.

W JPA klucz obcy to pole typu encji nadrzędnej z adnotacją @ManyToOne:

@ManyToOne(fetch = FetchType.LAZY, optional = false)
@JoinColumn(name = "table_id", nullable = false)
private CafeTable table;
Element Znaczenie
@ManyToOne wiele wierszy tej tabeli wskazuje na jeden wiersz tabeli nadrzędnej; w bazie powstaje kolumna klucza obcego i ograniczenie foreign key
@JoinColumn(name = "table_id") nazwa kolumny klucza obcego: <tabela_nadrzędna>_id. Bez niej Hibernate nazwałby kolumnę od nazwy pola (R3.01)
nullable = false, optional = false rezerwacja bez stolika nie ma sensu, więc kolumna jest wymagana (not null). Relacja opcjonalna, np. gość bez konta, nie ma tych ustawień
fetch = FetchType.LAZY Hibernate pobiera stolik dopiero wtedy, gdy kod o niego zapyta (getTable()), a nie przy każdym odczycie rezerwacji. Domyślnie jest EAGER, czyli zawsze (R3.06)
typ pola: encja, nie Long w Javie trzymacie obiekt CafeTable, w bazie jest liczba table_id. Tłumaczenie robi Hibernate

Hibernate generuje z tego dwie rzeczy: kolumnę w create table i osobne polecenie alter table z ograniczeniem klucza obcego:

create table reservation (
    deposit numeric(10,2) not null,
    party_size integer not null,
    guest_id bigint not null,          -- klucz obcy: gość
    id bigint generated by default as identity,
    starts_at timestamp(6) not null,
    table_id bigint not null,          -- klucz obcy: stolik
    status enum ('CANCELLED','CONFIRMED','DONE','NEW') not null,
    primary key (id)
)

alter table if exists reservation
    add constraint FKs87ss6lovy66qn86ra7rbc8e1
    foreign key (table_id)
    references cafe_table

Ograniczenie foreign key pilnuje, żeby table_id zawsze wskazywało istniejący stolik. Dlatego w data.sql najpierw muszą powstać stoliki, a dopiero potem rezerwacje (część F).

B2. Rodzaje relacji

Relacja Przykład W JPA Gdzie jest klucz obcy
wiele-do-jednego wiele rezerwacji → jeden stolik @ManyToOne + @JoinColumn w encji podrzędnej w tabeli podrzędnej (reservation.table_id)
jeden-do-wielu (strona odwrotna) stolik → jego rezerwacje @OneToMany(mappedBy = "table") + List<Reservation> w encji nadrzędnej nigdzie nowego: to tylko drugi koniec tej samej relacji (R3.03)
wiele-do-wielu rezerwacja ↔ dodatki (tort, kwiaty) encja łącząca z dwiema @ManyToOne i własnymi kolumnami (ilość, uwagi) w tabeli łączącej (reservation_extra.reservation_id, extra_id)
jeden-do-jednego gość ↔ konto użytkownika @OneToOne + @JoinColumn; rzadko, zwykle wystarcza @ManyToOne w tabeli, która wskazuje (guest.user_account_id)

Zasada praktyczna: relację buduje pole @ManyToOne. @OneToMany to dodatek, który tylko pozwala przejść od stolika do listy rezerwacji w Javie; bez mappedBy Hibernate potraktowałby go jako osobną relację i utworzył dodatkową tabelę łączącą cafe_table_reservations, której nikt nie planował.

B3. Przykład: kawiarnia z relacjami

Tabele z LAB 02 (cafe_table, menu_item, guest) łączymy nową tabelą reservation. Rezerwacja wskazuje na stolik i na gościa, a gość na konto użytkownika z szablonu. Wy w częściach D–F robicie to samo na tabelach ze swojego projektu.

Rezerwacja, klasa Reservation w booking.entity, dwie relacje @ManyToOne:

package pl.wsb.kawiarnia.booking.entity;

import jakarta.persistence.*;
import pl.wsb.kawiarnia.seating.entity.CafeTable;
import java.math.BigDecimal;
import java.time.LocalDateTime;

@Entity
@Table(name = "reservation")
public class Reservation {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "guest_id", nullable = false)
    private Guest guest;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "table_id", nullable = false)
    private CafeTable table;

    @Column(name = "starts_at", nullable = false)
    private LocalDateTime startsAt;

    @Column(name = "party_size", nullable = false)
    private Integer partySize;

    @Enumerated(EnumType.STRING)
    @Column(name = "status", nullable = false, length = 20)
    private ReservationStatus status;

    @Column(name = "deposit", nullable = false, precision = 10, scale = 2)
    private BigDecimal deposit;

    protected Reservation() {
    }

    public Reservation(Guest guest, CafeTable table, LocalDateTime startsAt, Integer partySize, BigDecimal deposit) {
        this.guest = guest;
        this.table = table;
        this.startsAt = startsAt;
        this.partySize = partySize;
        this.status = ReservationStatus.NEW;
        this.deposit = deposit;
    }

    // gettery: Code → Generate…
}

Gość dostaje relację do konta użytkownika. Konto to logowanie (e-mail, rola), gość to dane biznesowe (imię, telefon, adres). Nie każdy gość ma konto, więc relacja jest opcjonalna: bez optional = false i bez nullable = false:

import pl.wsb.kawiarnia.account.domain.UserAccount;

@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "user_account_id")
private UserAccount account;

Stolik może dostać stronę odwrotną. To opcjonalne: nie tworzy kolumny, tylko pozwala w Javie przejść od stolika do jego rezerwacji. Wartość mappedBy to nazwa pola @ManyToOne w encji podrzędnej (Reservation.table):

@OneToMany(mappedBy = "table")
private List<Reservation> reservations = new ArrayList<>();

Dane startowe. W kolumnie klucza obcego wpisujecie numer wiersza tabeli nadrzędnej. Baza numeruje wiersze od 1 w kolejności poleceń insert, więc pierwszy stolik z sekcji cafe_table ma id = 1, drugi id = 2 itd. Sekcja tabeli nadrzędnej musi być wyżej niż sekcja tabeli podrzędnej:

-- ===== LAB 02 · cafe_table =====            (id: 1, 2, 3)
insert into cafe_table (number, seats, room, active) values
    (1, 2, 'sala główna', true),
    (2, 4, 'sala główna', true),
    (3, 6, 'ogródek',     false);

-- ===== LAB 02 · guest =====                 (id: 1, 2, 3; konta z sekcji user_account: 1 = Ola, 2 = Kuba)
insert into guest (full_name, phone, user_account_id, street, city, postal_code) values
    ('Anna Kowalska',  '600100200', 1,    'Ruska 12',      'Wrocław', '50-079'),
    ('Jan Nowak',      null,        2,    null,            null,      null),
    ('Ewa Wiśniewska', '600500600', null, 'Świdnicka 3/4', 'Wrocław', '50-066');

-- ===== LAB 03 · reservation =====           (guest_id i table_id wskazują wiersze powyżej)
insert into reservation (guest_id, table_id, starts_at, party_size, status, deposit) values
    (1, 1, '2026-11-14 18:00:00', 2, 'NEW',       20.00),
    (1, 2, '2026-11-15 12:00:00', 4, 'CONFIRMED', 40.00),
    (2, 2, '2026-11-16 19:00:00', 3, 'NEW',        0.00);

Anna ma dwie rezerwacje, Ewa nie ma konta. Reguła R3.04 sprawdza, że dla każdej relacji co najmniej jeden wiersz ma wypełniony klucz obcy.

B4. Ściąga: wiele-do-wielu, LAZY, pytania inwestora

Wiele-do-wielu. Rezerwacja może mieć wiele dodatków (tort, kwiaty), a dodatek trafia do wielu rezerwacji. Para „rezerwacja + dodatek” ma własne dane (ilość, uwagi), więc modelujemy ją encją łączącą z dwiema relacjami @ManyToOne. Adnotacja @ManyToMany ukrywa tabelę łączącą i nie pozwala dodać do niej kolumn; używa się jej tylko wtedy, gdy para nie ma żadnych własnych danych, i wtedy z @JoinTable(name = "…") (R3.05).

@Entity
@Table(name = "reservation_extra",
        uniqueConstraints = @UniqueConstraint(columnNames = {"reservation_id", "extra_id"}))
public class ReservationExtra {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "reservation_id", nullable = false)
    private Reservation reservation;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "extra_id", nullable = false)
    private Extra extra;

    @Column(name = "quantity", nullable = false)
    private Integer quantity;

    @Column(name = "note", length = 120)
    private String note;

    protected ReservationExtra() {
    }
}

LAZY i EAGER. Przy EAGER (domyślnie dla @ManyToOne) odczyt jednej rezerwacji pobiera od razu także gościa i stolik, nawet gdy kod potrzebuje tylko daty. Przy stu rezerwacjach to setki zbędnych zapytań. LAZY odkłada pobranie do pierwszego wywołania gettera. Dlatego każde @ManyToOne i @OneToOne piszemy z fetch = FetchType.LAZY (R3.06).

Pytania inwestora. W opisie pomysłu zapisaliście pięć pytań biznesowych. Z relacjami baza umie na nie odpowiedzieć: join łączy tabele po kluczu obcym, group by liczy albo sumuje w grupach. Dwa przykłady w konsoli H2:

-- Ile rezerwacji ma każdy gość?
select g.full_name, count(r.id) as rezerwacje
from guest g
join reservation r on r.guest_id = g.id
group by g.full_name
order by rezerwacje desc;

-- Które stoliki są zarezerwowane 15 listopada i przez kogo?
select t.number, t.room, r.starts_at, g.full_name
from reservation r
join cafe_table t on r.table_id = t.id
join guest g on r.guest_id = g.id
where cast(r.starts_at as date) = '2026-11-15'
order by r.starts_at;

ZadanieD · Wybór relacji i przewidywanie

Na podstawie tabel z LAB 02 wybierzcie co najmniej dwie relacje wiele-do-jednego (R3.01). Dla każdej ustalcie:

Jedna z relacji wskazuje na konto użytkownika UserAccount (R3.02): encja osoby, która korzysta z aplikacji (klient, gość, autor ogłoszenia, właściciel zgłoszenia). ZadanieE · Relacje w kodzie

Każdą relację wprowadzacie w dwóch krokach: pole w encji (E1) i klucze obce w data.sql (F1). Dopóki nie zrobicie obu, aplikacja nie wystartuje: kolumna not null bez wartości w insert zatrzymuje wczytywanie danych. To normalne.

E1. Pole @ManyToOne w encji podrzędnej

Otwórzcie encję podrzędną (np. rezerwację) i dopiszcie pole typu encji nadrzędnej. Szkielet, który uzupełniacie własnymi nazwami:

@ManyToOne(fetch = FetchType.LAZY, optional = false)
@JoinColumn(name = "<tabela_nadrzędna>_id", nullable = false)
private <EncjaNadrzędna> <pole>;
  • Relacja opcjonalna (np. gość bez konta): usuńcie optional = false i nullable = false.
  • Encja z innego modułu: Alt+Enter → Import class, np. pl.wsb.<projekt>.seating.entity.CafeTable.
  • Konstruktor: dodajcie nowe pole do konstruktora z argumentami (Code → Generate… → Constructor albo ręcznie) i wygenerujcie getter. Setterów nie generujcie.
  • Pole trzyma obiekt, nie Long: private CafeTable table, nie private Long tableId.

E2. Relacja do konta użytkownika

W encji osoby (albo obiektu ze statusem, część D) dopiszcie pole typu UserAccount z pakietu pl.wsb.<projekt>.account.domain:

@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "user_account_id")
private UserAccount account;

Klasy UserAccount nie zmieniacie i nie przenosicie.

E3. Strona odwrotna (opcjonalnie)

Jeśli chcecie w encji nadrzędnej mieć listę wierszy podrzędnych (stolik → rezerwacje), dopiszcie pole z mappedBy równym nazwie pola @ManyToOne z encji podrzędnej (R3.03):

@OneToMany(mappedBy = "<pole @ManyToOne w encji podrzędnej>")
private List<<EncjaPodrzędna>> <pole> = new ArrayList<>();

To pole nie tworzy kolumny i nie wymaga danych w data.sql. Bez mappedBy Hibernate utworzy dodatkową tabelę łączącą.

E4. Sprawdzenie w logu i commit

  1. Uzupełnijcie klucze obce w data.sql (F1), potem Rerun w oknie Run.
  2. W logu znajdźcie create table <tabela_podrzędna> i niżej alter table … add constraint … foreign key. Porównajcie z przewidywaniem z części D: nazwa kolumny, not null, tabela, na którą wskazuje klucz obcy.
  3. Git → Commit z opisem, np. „Relacja rezerwacja → stolik”, potem Push.
  4. Kolejna relacja: znowu od E1.

ZadanieF · Dane powiązane i konsola H2

F1. Klucze obce w data.sql

Do polecenia insert tabeli podrzędnej dopiszcie kolumnę klucza obcego i w każdym wierszu numer wiersza tabeli nadrzędnej (wzór w B3). Zasady:

  • Numery wierszy: baza numeruje od 1 w kolejności insert w danej sekcji. Pierwszy wiersz sekcji cafe_table to table_id = 1. Konta z sekcji user_account też są numerowane od 1, łącznie z kontami demo z szablonu.
  • Kolejność sekcji: sekcja tabeli nadrzędnej wyżej niż sekcja tabeli podrzędnej. W razie potrzeby przenieście całą sekcję (zaznaczcie, Cut, Paste).
  • Relacja opcjonalna: w części wierszy może być null, ale co najmniej jeden wiersz ma wartość (R3.04).
  • Dane sensowne: ten sam gość w dwóch rezerwacjach, stolik bez rezerwacji. Takie dane dają ciekawe odpowiedzi na pytania inwestora (F3).

F2. Zaplanowana awaria: wiersz podrzędny przed nadrzędnym

Zróbcie to celowo, raz, na działającym projekcie:

  1. Przenieście sekcję tabeli podrzędnej (np. reservation) nad sekcję tabeli nadrzędnej (np. guest) i zróbcie Rerun.
  2. Aplikacja nie wystartuje. Znajdźcie w logu linię z Caused by i przeczytajcie ją w całości: 
    Referential integrity constraint violation: "FK8RDUAF1N8ES4JF5WAGBJHJEPJ:
    PUBLIC.RESERVATION FOREIGN KEY(GUEST_ID) REFERENCES PUBLIC.GUEST(ID) (CAST(1 AS BIGINT))"
    Baza mówi: rezerwacja wskazuje gościa o id = 1, a takiego gościa jeszcze nie ma.
  3. Przywróćcie kolejność sekcji i sprawdźcie, że aplikacja znowu startuje.

Ten komunikat zobaczycie jeszcze nieraz w przyszłych projektach. Teraz wiecie, co znaczy (pytanie kontrolne 2).

F3. Pytania inwestora w konsoli H2

Otwórzcie http://localhost:8080/h2-console (JDBC URL jdbc:h2:file:./data/wdtb, użytkownik sa, hasło puste). Najpierw sprawdźcie klucze obce:

select * from <tabela_podrzędna>;

Potem wybierzcie dwa pytania inwestora z Waszego opisu pomysłu, na które da się odpowiedzieć dzięki nowym relacjom, i napiszcie do nich zapytania z join (wzór w B4). Gdy zapytanie zwraca sensowny wynik, zapiszcie je jako komentarz na końcu data.sql, żeby wróciło na LAB 04:

ZadanieG · Na ocenę 5: wiele-do-wielu, LAZY, repozytorium

G1. Relacja wiele-do-wielu jako encja łącząca (R3.05)

Wybierzcie parę tabel, między którymi jest relacja wiele-do-wielu z opisu pomysłu (rezerwacja ↔ dodatki, zamówienie ↔ produkty, uczestnik ↔ wydarzenia). Utwórzcie encję łączącą według wzoru ReservationExtra z B4:

  • dwie relacje @ManyToOne z @JoinColumn(…, nullable = false) oraz co najmniej dwie własne kolumny (ilość, uwagi, data dodania, cena w chwili zakupu),
  • @UniqueConstraint na parze kluczy obcych, żeby ta sama para nie powtórzyła się dwa razy,
  • sekcja -- ===== LAB 03 · <tabela_łącząca> ===== w data.sql z co najmniej 3 wierszami, pod sekcjami obu tabel nadrzędnych.

G2. LAZY na każdej relacji (R3.06)

Sprawdźcie, że każde pole @ManyToOne i @OneToOne w Waszych encjach ma fetch = FetchType.LAZY. Reguła podaje listę pól do poprawy.

G3. Repozytorium z zapytaniem przez relację (R3.07)

Repozytorium to interfejs Spring Data: nie piszecie implementacji, Spring buduje SQL z nazwy metody. Utwórzcie pakiet pl.wsb.<projekt>.<moduł>.repository (obok entity tego modułu) i w nim interfejs:

package pl.wsb.<projekt>.<moduł>.repository;

import org.springframework.data.jpa.repository.JpaRepository;
import pl.wsb.<projekt>.<moduł>.entity.<Encja>;
import java.util.List;

public interface <Encja>Repository extends JpaRepository<<Encja>, Long> {

    List<<Encja>> findBy<PoleRelacji>_<PoleEncjiNadrzędnej>(<typ> wartość);
}

Nazwa metody prowadzi przez relację: findByGuest_FullName(String fullName) znaczy „rezerwacje, których gość ma podane imię i nazwisko” (pole guest w Reservation, potem pole fullName w Guest). Inne przykłady: findByTable_Number(Integer number), countByAccount_Email(String email), findByOwner_Id(Long id). Po Rerun aplikacja musi wystartować: Spring Data sprawdza nazwę metody przy starcie (błąd No property … found oznacza literówkę).

G4. Test repozytorium

Żeby zobaczyć wynik zapytania, piszecie pierwszy test. Prawy przycisk na pakiecie <moduł>.repository w katalogu src/test/java (IntelliJ utworzy pakiet, jeśli go nie ma) → New → Java Class → <Encja>RepositoryTest:
